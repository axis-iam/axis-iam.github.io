# Authentication

Vertex offers four UI integration modes. Choose where the form lives and who renders it; authentication policy and
identity remain owned by the Application.

| Mode | UI owner | Credential handling | Best fit |
| --- | --- | --- | --- |
| [Hosted](./hosted/) | Vertex | Vertex origin | Lowest application security surface and centralized policy UX |
| [Embedded](./embedded/) | Application | Application-rendered form/provider controls | Branded inline flows with more app responsibility |
| [Dialog](./dialog/) | Vertex SDK component | Vertex SDK orchestration in app UI | Prebuilt modal UX without implementing every state |
| [Custom](./custom/) | Application | Public SDK hooks and application-rendered controls | A fully custom interface using the supported authentication flow |

Hosted authentication uses Authorization Code + S256 PKCE. Embedded and Custom use a controlled authentication
transaction for password, email/SMS codes, magic links, Provider authentication and required MFA. Successful
transaction completion returns an authorization code, which the SDK exchanges through OAuth with the original
PKCE binding. Dialog presents the Hosted or Embedded flow selected by the application.

All browser modes use a public SPA client with no secret, an exact allowed origin, registered callback URIs,
OAuth `state`, and S256 PKCE. Use the SDK rather than constructing credential or Provider requests yourself.
`clientId` identifies a client belonging to the Application; it does not make authentication policy client-owned.
Tokens stay in memory by default. Session storage requires explicit configuration.

This guide describes the current SDK source candidate. Check the [JavaScript SDK installation status](../sdk/javascript/)
before choosing an artifact; an older preview package does not automatically contain these APIs.

Server-rendered WEB integrations use a confidential client. Interactive code exchange requires both the server-held
client secret and the matching PKCE verifier.
